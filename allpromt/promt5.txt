Do not create a static settings page or fake payment buttons.

==================================================
PAYMENT GATEWAYS
==================================================

Support multiple payment gateways, including:

1. Flutterwave
2. Stripe
3. PayPal
4. Cryptocurrency payment gateway
5. Manual Bank Transfer
6. Any additional gateway that can be safely integrated into the existing architecture

==================================================
IMPORTANT SECURITY REQUIREMENTS
==================================================

Never hardcode API credentials.

Never expose secret keys in:

- Blade templates
- JavaScript
- Public API responses
- Logs
- Guest pages

Store credentials securely using Laravel environment variables or a secure encrypted database settings system.

If credentials are stored in the database, encrypt sensitive credentials before saving them and decrypt them only on the server when needed.

Mask sensitive credentials in the Admin UI.

Example:

FLWSECK_TEST-**************1234

Only authorized Admin users can view or update payment settings.

==================================================

The Admin must be able to turn payment gateways on or off.

Example:

Flutterwave: ON
Stripe: ON
PayPal: OFF
Crypto: ON
Bank Transfer: ON

Only enabled gateways should appear to the Guest on the payment page.

If a gateway is disabled:

- It must not appear as a payment option.
- It must not be usable through a direct URL.
- The backend must reject attempts to use it.

The Admin's toggle setting must control both:

1. Frontend visibility
2. Backend payment processing

FLUTTERWAVE
==================================================

Implement Flutterwave Standard Checkout.

- Create transaction server-side.
- Generate a unique transaction reference.
- Redirect the Guest to Flutterwave checkout.
- Handle callback.
- Verify the transaction server-side.
- Confirm transaction reference.
- Confirm amount.
- Confirm currency.
- Confirm successful status.
- Update payment only after successful verification.
- Support webhook notifications.
- Validate webhook authenticity.
- Make webhook processing idempotent.

Never mark a payment as successful only because the Guest returned from the payment page.

==================================================
STRIPE
==================================================

Implement Stripe Checkout or the most appropriate secure Stripe payment flow.

Requirements:

- Create Checkout Session server-side.
- Use the correct amount and currency.
- Store the internal payment reference.
- Handle successful payment.
- Verify payment using Stripe's server-side API/webhook.
- Prevent duplicate payment processing.
- Never expose Stripe secret keys.

==================================================
PAYPAL
==================================================

Implement a secure PayPal payment flow.

- Create order server-side.
- Redirect Guest to PayPal approval.

- Verify the payment.
- Match the payment amount and currency.
- Update the payment status only after successful verification.

CRYPTOCURRENCY PAYMENTS
==================================================

Implement cryptocurrency payment support using a legitimate payment processor/API rather than attempting to directly process blockchain payments insecurely.

The Admin must be able to:

- Enable/disable crypto payments.
- Configure supported cryptocurrency options.
- Configure payment processor credentials.
- View payment status.

The system must:

- Generate a unique payment reference.
- Generate a payment request through the selected crypto provider.
- Display payment instructions or checkout.
- Track pending, confirmed, failed, and expired payments.
- Verify payment through the provider/webhook.
- Never manually mark crypto payments as successful without verification.

Do not use fake crypto payment confirmation.

- Generate a unique payment reference.
- Allow the Guest to submit proof of payment if required.
- Keep payment status as Pending until Admin verifies it.
- Allow Admin to Approve or Reject the payment.

Never automatically mark manual bank transfers as paid.

==================================================
PAYMENT TRANSACTION SECURITY
==================================================

Every payment must have:

- Internal payment ID
- Unique transaction reference
- Gateway name
- Gateway transaction ID
- Amount
- Currency
- Shipment ID
- Payment request ID
- Status
- Timestamps

Use database transactions where necessary.

Prevent:

- Duplicate payment processing
- Amount manipulation
- Currency manipulation
- Transaction reference reuse
- Unauthorized payment status changes
- Guest access to other shipments
- Payment confirmation without server-side verification

The amount used for payment must come from the server-side payment request.

Never trust the amount sent by the Guest's browser.

WEBHOOK SYSTEM
==================================================

Implement gateway webhook endpoints where required.

- Validate authenticity/signature.
- Identify the correct payment.
- Verify the transaction with the gateway where appropriate.
- Be idempotent.
- Avoid duplicate processing.
- Return the correct response to the gateway.

If the same webhook is received multiple times, the payment must not be processed multiple times.
